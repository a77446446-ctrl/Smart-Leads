# Аудит и первая реализация Smart Leads

## Проверка исходной копии

Архив: `Smart Leads.rar`, исходники внутри `Smart Leads/MAKS-LEAD-HUB/`.
217 файлов исходного кода, CSS, конфигурации, тестов, миграций и документации сверены с CRC32 архива. Пропусков и отличий нет. Это подтверждение целостности выбранных исходников, а не полноты копирования всех данных, кэшей и Git-истории архива.

В коммерческую основу перенесены 213 файлов. Для каждого записан исходный SHA-256 в `source-integrity.json`. Созданные затем файлы и изменения бренда — уже новая разработка.

Не перенесены: .env, базы, сессии, реальные загрузки, отладочные снимки, история Git и логи, старые логотипы, подтверждения Яндекс, виртуальное окружение Python и кэши. Устаревший seed создавал фиксированного администратора с telegramId, которого нет в текущей схеме; он и скрипты очистки данных исключены.

## Архитектура

Модульное Next.js-приложение и отдельный Python worker, PostgreSQL через Prisma, доставка MAX через существующую очередь BotDelivery. Первый выпуск рассчитан на отдельную установку для каждого клиента, а не на общую многопользовательскую базу организаций.

| Область | Текущая реализация | Дальнейшая работа |
| --- | --- | --- |
| Вход | /login, /consent, /api/auth/max, подписанная cookie | Telegram и модель внешних идентификаторов |
| Пользователь | /dashboard, /my-leads, /archive, /subscriptions, /profile | Поиск по материалам, новостной режим |
| Администратор | /admin, лиды, категории, пользователи, платежи, settings, discovery | Разделение прав владельца и технических операций |
| Бренд | Новый /admin/branding и /api/admin/branding | Полная проверка на отдельной БД, остальные темы оформления |
| MAX-парсер | scripts/parser_worker.py и src/services/max-parser.ts | Использовать сохранённый контракт |
| Доставка MAX | bot-outbox.ts, max-bot.ts, webhook, MaxBotChat | Сохранить транзакции и дедупликацию |
| Telegram | Нет входа и доставки | Независимая интеграция и очередь |
| Медиа | Есть загрузка изображений интерфейса | Модель вложений, хранение, сроки жизни и доставка |
| Платежи | PaymentOrder, ЮKassa, согласия, журнал | Тестовый магазин и сверка денежных единиц |
| Развёртывание | Dockerfile, cron, миграции, health API | Раздельные секреты, тест восстановления, мастер установки |

Полный список страниц и API можно получить из дерева src/app. Главные группы API: auth, admin, leads, buy-lead, payments, legal, preferences, profile, internal, webhooks, ingest, uploads, health. Диагностические dev/test-маршруты унаследованы; перед выпуском проверить необходимость их поставки.

Основные модели: User, BlockedMaxUser, Category, Subscription, Lead, Purchase, Transaction, Setting, MaksAccount, ParserLease, ParserSeenMessage, TargetChat, DiscoveryRun, BotDelivery, MaxBotChat, UserCategoryPreference, LegalAcceptance, PaymentOrder.

## Бренд

Настройки хранятся одним объектом в существующей таблице Setting. Новая миграция не нужна. Изменять бренд может только действующий администратор: используются существующие серверные проверки роли.

Сервер выбирает только публичные поля, ограничивает размер фактически прочитанного JSON, проверяет длины строк, email, цвет и путь к логотипу. Произвольные внешние изображения и исполняемые URL не принимаются. Логотип загружается через существующий API с проверкой формата, сигнатуры и размера. Нечитаемый тёмный акцент отклоняется.

Общий React-контекст передаёт публичный бренд страницам. Сервер формирует метаданные и CSS-переменные из тех же настроек. Запрос к базе повторно не выполняется в пределах одного серверного рендера. При отсутствии базы используется Smart Leads.

Нейтрализованы вход, общий логотип, шапка ленты, мобильная и настольная админка, подвал, профиль, SEO и описание пополнения баланса. Домен исходного проекта и подтверждения Яндекс в новой версии не используются. Контакт поддержки берётся из юридических настроек, а при его отсутствии — из бренда.

Пока остаётся старое приветствие MAX в защищённом max-bot.ts. Новое welcomeText управляет только страницей входа. Полную смену текстов бота следует делать отдельным узким изменением после согласования сохранения проверенной цепочки. Имена ботов задаются существующей переменной MAX_BOT_USERNAME. Названия категорий уже управляются из админки.

## Ограничения и найденные проблемы

1. maxId в User обязателен и уникален. Для Telegram нельзя создавать фиктивные MAX ID. Нужны внешние идентичности с уникальностью пары провайдер/идентификатор, миграция текущих пользователей и безопасное связывание аккаунтов. Роли назначаются внутри приложения.
2. parser_worker.py возвращает сообщения вида {text, id}, а не вложения. Ссылки внутри текста не являются полноценным контрактом медиа. Для извлечения изображений, видео и аудио из MAX потребуется отдельное разрешение на изменение worker; до него можно готовить хранение и ручной импорт вложений.
3. Для Telegram нужна своя очередь, независимая от BotDelivery MAX. Доставка должна учитывать повтор события, временные ошибки, недоступность получателя и остановку бота.
4. Скопированная .venv ссылалась на Python по отсутствующему пути исходного компьютера. Она исключена, Python-окружение следует устанавливать заново.
5. Архитектурные документы прежней системы местами устарели: package.json содержит Next.js 15.5.24, тогда как старое описание указывает 14.
6. Документация о копейках расходится с текущими money.ts и именами переменных. До коммерческих платежей нужен отдельный аудит миграций, фактических данных и формата сумм. Автоматическая смена единиц недопустима.
7. Исходный CI использовал Node.js 18 при engines 22.x; в коммерческой версии выбран 22.x.
8. Унаследованный Dockerfile требует явного исключения приватных файлов из COPY. Добавлен .dockerignore, корень сборки должен быть commercial.
9. Исходное npm start выполняет миграции, backfill и cron. Оно не использовалось для проверки.
10. Новый модуль бренда проверяется отдельно; реальные сохранение в PostgreSQL, MAX-вход и загрузка логотипа требуют тестового экземпляра.

## Унаследованные падения тестов

- auth-security: статическая проверка ожидает bonusGrant.count === 1, код проверяет эквивалентную промежуточную переменную bonusGrantCount. Это несоответствие формы теста; бизнес-логика здесь не изменялась.
- lead-category: ожидаемая проверка categoryMatched отсутствует в целевой ветке max-parser.ts. Это потенциальное расхождение поведения и требования; его нельзя скрывать изменением теста. Обвязка парсера сохранена побайтно для первого этапа отделения версии.

Эти падения существовали до коммерческих изменений и сохраняются явно.

1. Завершить приёмку нейтрального бренда на новой БД; отдельно разобрать два старых падения.
2. Разделить права владельца и технические операции, сохранив доступ текущего MAX-администратора.
3. Добавить внешние идентификаторы и Telegram-вход по актуальной официальной спецификации.
4. Добавить независимую очередь Telegram с настройкой категорий.
5. Подготовить модель вложений и обработку файлов; согласовать извлечение медиа из MAX.
6. Собрать мастер подключения и изолированное развёртывание.
7. Создать вымышленные демо-данные и материалы для продажи.
8. Провести весь сценарий новой установки, доставки, обновления и восстановления.
