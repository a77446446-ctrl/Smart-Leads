# Настройка экземпляра владельцем

Каждому клиенту выдаётся отдельный экземпляр и отдельная база данных. Менеджер один раз задаёт инфраструктурные переменные в Coolify. После первого входа администратор клиента открывает **Интеграции** и самостоятельно вводит токены MAX, данные входа Telegram, магазин ЮKassa и реквизиты оператора.

## Что остаётся в Coolify

Примеры ниже вымышленные. Значения после `=` нужно заменить целиком; секреты должны быть разными и случайными. Уже используемые секреты не менять без плана переноса.

```dotenv
# Адрес PostgreSQL для приложения. Если пароль содержит @, :, / или ?, его нужно URL-кодировать.
DATABASE_URL=postgresql://smartleads:example_password@postgres:5432/smartleads?schema=public
# Прямой адрес PostgreSQL для миграций; без пулера может совпадать с DATABASE_URL.
DIRECT_URL=postgresql://smartleads:example_password@postgres:5432/smartleads?schema=public
# Публичный HTTPS-домен без завершающего слеша.
NEXT_PUBLIC_APP_URL=https://leads.example.org
# Случайный постоянный секрет от 32 символов для входа и шифрования клиентских настроек.
AUTH_SESSION_SECRET=EXAMPLE_ONLY_AUTH_8e7f9c12ad34ef56bc78
# Другой случайный секрет от 32 символов для внутреннего планировщика.
CRON_SECRET=EXAMPLE_ONLY_CRON_57bca013fe89d426a781
# Отдельный постоянный ключ от 32 символов для прокси парсера.
PARSER_PROXY_ENCRYPTION_KEY=EXAMPLE_ONLY_PROXY_6ac927e1f8d43b50ae71
# Отдельный постоянный ключ от 32 символов для резервных копий MAX-сессий.
PARSER_SESSION_ENCRYPTION_KEY=EXAMPLE_ONLY_SESSION_9c41a7f52e80d63baf19
# Путь внутри контейнера; постоянное хранилище Coolify подключается к /app/data.
PARSER_SESSIONS_DIR=/app/data/sessions
# Личные числовые ID первоначального администратора. Списки допускают несколько ID через запятую.
ADMIN_TELEGRAM_IDS=987654321
ADMIN_MAX_IDS=
# Для ПЕРВОГО входа нужен хотя бы один уже действующий способ авторизации.
# Если MAX-бота пока нет, менеджер вводит данные Telegram из BotFather → Login Widget.
TELEGRAM_CLIENT_ID=123456789
TELEGRAM_CLIENT_SECRET=EXAMPLE_ONLY_TelegramClientSecret_1234567890
```

`DIRECT_URL` не требуется отдельно, если `DATABASE_URL` уже ведёт напрямую в PostgreSQL. Для локального тестирования можно использовать существующую конфигурацию `.env.local`. Секреты не отправлять в переписке и не помещать в GitHub.

Если другой сервис будет отправлять лиды в `POST /api/ingest`, задайте также отдельный `INGEST_SECRET` длиной от 32 символов. Для встроенного MAX-парсера эта переменная не нужна. `PARSER_PYTHON_EXECUTABLE` и `PARSER_AUTH_HEADLESS` в штатном Docker-образе уже имеют рабочие значения по умолчанию. `NODE_EXTRA_CA_CERTS` добавляйте только при подтверждённой проблеме TLS с MAX API.

Первый вход — исключение из самообслуживания: пока клиент не вошёл в админку, он не может задать данные собственного бота из приложения. Менеджер первоначально задаёт Telegram Client ID/Secret и ID администратора в Coolify либо MAX-бота и MAX ID. Затем клиент может заменить данные интеграции через интерфейс и больше не обращаться к менеджеру при обычных изменениях.

Списки `ADMIN_TELEGRAM_IDS` и `ADMIN_MAX_IDS` пока управляются через Coolify. Изменение состава администраторов требует обновления этих переменных и redeploy; не передавайте статус администратора через обычное поле роли пользователя.

## Что настраивает владелец в приложении

- **MAX:** токен и никнейм собственного бота, случайный секрет webhook. После сохранения нажать «Подключить webhook MAX». Нужен бот, прошедший модерацию платформы MAX, и публичный HTTPS-домен Mini App.
- **Telegram:** Client ID и Client Secret из BotFather → Login Widget. Там же разрешить адрес сайта и `https://ВАШ-ДОМЕН/api/auth/telegram/callback`. Токен бота для веб-входа не используется.
- **ЮKassa:** Shop ID, секретный ключ API и правильный код НДС своего магазина. Для уведомлений ЮKassa указать `https://ВАШ-ДОМЕН/api/webhooks/yookassa`.
- **Реквизиты:** выбрать организацию, ИП или самозанятого, указать реальные имя/наименование, ИНН и контактные адреса. Для самозанятого без ИП приложение не требует ОГРНИП и юридический адрес. Типовые тексты оферты, политики и согласия нужно проверить под фактическую модель бизнеса до публичного запуска.

Клиентские значения шифруются в таблице `Setting` ключом, производным от `AUTH_SESSION_SECRET`; при перезапуске приложения они загружаются из базы. Экземпляр рассчитан на один контейнер приложения: при горизонтальном масштабировании потребуется синхронизировать изменения конфигурации между процессами. Если значения интеграций уже заданы в Coolify, они работают до переноса; после сохранения этих же значений в приложении можно удалить их из Coolify и выполнить redeploy. Не удалять и не менять инфраструктурные ключи.

Реальные платежи блокируются, пока не указаны необходимые реквизиты и пользователь не принял актуальные документы. Изменение реквизитов меняет контрольную сумму документов и требует нового принятия пользователями.
